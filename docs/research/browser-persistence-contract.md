## Attachment bytes and previews

IndexedDB record values support structured serialization, including `File` and `Blob`. Values are copied into storage rather than retained as references to mutable application objects. Attachment bytes can therefore be stored with their metadata and retrieved after reload. [IndexedDB values](https://w3c.github.io/IndexedDB/#values).

`URL.createObjectURL()` creates a preview URL for a Blob or File. Blob URLs belong to a document's lifetime and the browser releases them on unload. Implementation implication: store bytes and metadata, recreate preview URLs after loading, and revoke URLs when their preview is no longer accessible. Saving the URL string alone cannot preserve an attachment. [Object URL creation](https://developer.mozilla.org/en-US/docs/Web/API/URL/createObjectURL_static), [Blob URL lifetime](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob#memory_management).

`crypto.subtle.digest("SHA-256", bytes)` can compute a digest of an uploaded file's bytes. It requires a secure context and accepts the whole buffer rather than streaming input. Implementation implication: read and hash the file before opening a write transaction, and check API availability. Hashing only the bytes does not include filename or MIME metadata. Whether matching content should be rejected remains a product decision. [SubtleCrypto digest](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest).

Web Storage holds strings and its operations synchronously block JavaScript. MDN documents about 5 MiB for localStorage per origin. A permitted 5,000,000-byte attachment is already close to that entire allowance before string encoding or other data. Implementation implication: localStorage cannot support the agreed multi-attachment data contract reliably. [Storage interface](https://html.spec.whatwg.org/multipage/webstorage.html#the-storage-interface), [Web Storage execution](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API), [Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria#web_storage).

## Atomic commits and transaction lifetime

An IndexedDB transaction is atomic and can include several object stores in one database. Overlapping read/write transactions serialize. Implementation implication: read the current record and its version, check the expected version and current domain permissions, then write all related records in the same read/write transaction. Reading first in a separate transaction would leave a race before writing. An atomic commit can include application data, attachment references or bytes, activity, notifications, and an operation receipt. [IndexedDB transactions and scheduling](https://w3c.github.io/IndexedDB/#transaction-concept), [Multi-store transaction scope](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction#parameters).

Transaction `complete` signals successful commit. A request's `success` does not establish that the whole transaction succeeded. Implementation implication: resolve a successful mock write and display saved feedback only after transaction completion. An upload progress animation reaching its end does not establish persistence. [Transaction completion](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event).

Transactions are active in the task that creates them and during their request event callbacks, inactive in other tasks, and auto-commit once pending requests finish without further requests. Implementation implication: finish mock latency, sample fetching, and asynchronous file preparation before creating the transaction. Timers or unrelated awaited work inside a transaction can let it finish or make later requests fail. Keep version checks, pure domain calculations, and dependent requests within the transaction's valid lifetime. An `async` function alone does not extend that lifetime. [Transaction activity](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction).

An IndexedDB transaction cannot include writes to sessionStorage or localStorage. Implementation implication: placing an essential operation effect there creates a separate commit boundary. A wrapper library cannot turn independent browser storage APIs into one IndexedDB transaction. [Transaction scope](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction#parameters).

## Completion, retention, and failures

Logical commit is different from permanent retention. Firefox can deliver `complete` before the operating system flushes writes to disk. Transaction durability options are `default`, `strict`, and `relaxed` hints, whose support must be checked for the eventual browsers. No setting prevents explicit user deletion of site data. [Durability behavior](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction#firefox_durability_guarantees), [Durability option](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction#parameters).

Browser storage normally uses best-effort retention. Quotas vary, storage pressure can evict data, and private browsing usually deletes data when that mode ends. `navigator.storage.estimate()` returns estimates, not a reservation; a write can still fail with `QuotaExceededError`. `navigator.storage.persist()` requests stronger retention and returns whether it was granted, so its availability does not establish approval. [Quota and eviction rules](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [Persistent-storage request](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist).

IndexedDB opening can throw `SecurityError` synchronously when a storage key cannot be obtained, and opening also has asynchronous error events. Writes can abort because of quota, I/O failure, or shutdown. Implementation implication: handle synchronous API failures, open-request failures, transaction aborts, and unexpected connection closure. API presence or a successful read is insufficient evidence that a subsequent write will succeed. [Open algorithm](https://w3c.github.io/IndexedDB/#dom-idbfactory-open), [Open request errors](https://developer.mozilla.org/en-US/docs/Web/API/IDBFactory/open), [Shutdown and lost access](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB#warning_about_browser_shutdown).

## Cross-tab notices and the source of truth

BroadcastChannel delivers messages to listening contexts with matching channel names and storage partitions, excluding the sending channel object. The standard enumerates eligible recipients at posting time and provides no durable message log or later replay. [BroadcastChannel behavior](https://developer.mozilla.org/en-US/docs/Web/API/BroadcastChannel), [Storage partition nuance](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API), [Broadcast algorithm](https://html.spec.whatwg.org/multipage/web-messaging.html#broadcasting-to-other-browsing-contexts).

Implementation implication: announce a committed revision only after transaction completion, then have recipients reread IndexedDB. Treat a notice as a hint rather than an authoritative application snapshot. Recheck storage on startup and return to an active tab, because a notice may have been missed. Update the initiating tab directly. If notice delivery fails after commit, the saved data still exists; reread rather than report that the write failed or repeat its effects. [Transaction completion](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event), [Broadcast algorithm](https://html.spec.whatwg.org/multipage/web-messaging.html#broadcasting-to-other-browsing-contexts).

A localStorage `storage` event can notify other same-origin tabs; sessionStorage events do not cross top-level tabs. The writing window receives neither event. Web Storage supplies no general locking mechanism, so a read-modify-write sequence cannot safely enforce record versions across tabs. Implementation implication: a storage-event fallback can signal that a reread is needed, but cannot replace the transaction's version check. [Storage events](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event), [Web Storage concurrency](https://html.spec.whatwg.org/multipage/webstorage.html#introduction).

## Tab sessions and database startup

sessionStorage is separated by origin and top-level tab, and survives reloads and session restores. A page with an opener initially receives a copy of the opener's sessionStorage; later changes remain independent. Removing the opener prevents that documented copying. Implementation implication: subsequent identity switching can be tab-local, but sessionStorage alone does not promise that every newly opened tab starts signed out. Reading it can throw `SecurityError` when browser policy blocks storage. [Session storage behavior and exceptions](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage).

An IndexedDB upgrade waits for other open connections to close. Handle `versionchange` on existing connections and `blocked` on an opening or deleting request. Opening an older requested database version can produce `VersionError`. Browser APIs provide schema-change mechanisms, but do not validate an application's stored record shape or decide whether damaged data should be reset. [Upgrade coordination and version errors](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB#version_changes_while_a_web_app_is_open_in_another_tab).

## TanStack Start's browser boundary

Start SPA mode prerenders the root shell using the SSR build. Root loaders and server-specific root functionality can run during that build step. Matched routes appear after browser startup. Implementation implication: browser storage, session restoration, seeding, and BroadcastChannel initialization must not execute at module import or during root-shell rendering. Use a browser startup boundary and show a neutral shell until initialization finishes. [SPA shell and dynamic root data](https://tanstack.com/start/latest/docs/framework/react/guide/spa-mode).

Start's `createClientOnlyFn` throws when called on the server. It enforces an environment boundary but does not defer an eager call until browser startup. `createIsomorphicFn` supplies separate client and server implementations. These are framework facts, not a package or initialization-design choice. [Environment functions](https://tanstack.com/start/latest/docs/framework/react/guide/environment-functions).
