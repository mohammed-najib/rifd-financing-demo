## Vitest for pure TypeScript rules

Vitest supports TypeScript transformation and uses Node as its default test environment. Its jsdom and happy-dom environments emulate browser APIs; Browser Mode is a separate facility. A pure domain module therefore needs no DOM emulator to test validation, transition rules, comparisons and calculations. That last sentence is an inference from the documented environments and the agreed module boundary. [Vitest features](https://vitest.dev/guide/features.html), [test environments](https://vitest.dev/guide/environment.html).

Vitest can use a separate `vitest.config.*` rather than inheriting the application's Vite configuration, and `vitest run` executes once without watch mode. The current getting-started guide lists Vite at least 6.4.0 and Node at least 22.12.0. Those are the current guide's requirements, not a selection of compatible application packages. Verify the selected Start/Vite/Vitest versions together when the implementation manifest exists, and record them in the lockfile. [Vitest getting started](https://vitest.dev/guide/).

Runtime tests and compiler checks establish different facts. Vitest documents a separate type-testing facility using TypeScript tooling. Playwright transforms TypeScript but does not type-check the test suite and recommends running the compiler separately. A successful runtime suite must not substitute for the application's and tests' TypeScript checks. [Vitest type testing](https://vitest.dev/guide/testing-types.html), [Playwright TypeScript](https://playwright.dev/docs/test-typescript).

Implementation inference: use focused Node tests for the pure domain contract, including accepted and rejected commands, invalid submission, correction-target comparisons, dependent-check resets and repayment arithmetic. Verify browser persistence and concurrency through the real demo module in browser tests; passing a Node DOM or storage emulator does not establish actual browser transaction behavior. The storage facts and agreed cases remain in the existing persistence decision.

## Playwright for browser operations and journeys

Playwright's browser binaries are tied to its releases. Its default Chromium is an open-source build and may be ahead of released Google Chrome. The `chrome` channel can instead drive installed branded stable Chrome. Playwright's Firefox relies on patches and cannot drive ordinary branded Firefox; its WebKit is also patched and cannot drive branded Safari. Platform-dependent capabilities can vary by operating system. Therefore label evidence as stable Chrome automation, pinned Playwright Firefox automation, current Firefox manual checks, and WebKit compatibility automation as applicable. Record actual versions and the operating system. [Playwright browsers](https://playwright.dev/docs/browsers).

`page.evaluate()` executes JavaScript in the page's browser environment and can await browser-side work. The test process has a different JavaScript environment. Implementation inference: a test page can import the agreed demo module and invoke its typed operations inside a real browser, exercising the real IndexedDB implementation. Assert the public operation result and role-filtered reread rather than making the test reproduce the module's storage writes. [Playwright evaluation](https://playwright.dev/docs/evaluating).

Each test normally receives an isolated browser context. A context can contain multiple pages, including popups, while separate contexts isolate browser state. Same-origin pages in the same context are the appropriate setup for this demo's shared browser dataset, with independent tab sessions under the existing storage contract. Separate contexts are useful for test isolation, but would create separate datasets rather than model the applicant and reviewer sharing this local demo. [Playwright isolation](https://playwright.dev/docs/browser-contexts), [multiple pages](https://playwright.dev/docs/pages).

Playwright documents IndexedDB inclusion in storage snapshots through `storageState({ indexedDB: true })`, added in version 1.51. Ordinary non-persistent contexts do not save browsing data to disk after they are closed. Its authentication guide also says sessionStorage needs separate handling rather than the regular storage-state API. Therefore, test restoration by refreshing or reopening pages in the same context, and sign each tab in through the demo interface. Do not treat a storage-state file as proof of attachment-byte fidelity or tab-session restoration. [BrowserContext storage state](https://playwright.dev/docs/api/class-browsercontext#browser-context-storage-state), [session storage in tests](https://playwright.dev/docs/auth#session-storage).

Device presets simulate settings such as viewport, screen size, user agent and touch capability. Locale, timezone and offline network behavior can also be configured. These settings support responsive and interaction checks; they do not establish behavior on physical phones, phone keyboards, actual mobile Safari, or device storage conditions. WebKit and phone presets should be labelled as automation/emulation evidence. [Playwright emulation](https://playwright.dev/docs/emulation), [WebKit limits](https://playwright.dev/docs/browsers#webkit).

Implementation inference: use a fresh context per scenario, seed through normal startup, and use two same-context pages for version races, cross-tab reset and applicant/reviewer visibility. Use the agreed failure controls for reproducible errors. Keep genuine browser round trips and concurrent transactions for the cases where simulated failures alone cannot establish correctness. Screen checks can drive the normal UI; deeper transaction cases can invoke the same module through a test-only page. The mechanism must not add unrestricted storage access to product screens.

## Lighthouse conditions and signed-in routes

Lighthouse results vary with the page, network, hardware, resource contention and browser execution. Its own guidance recommends repeated runs and aggregate results, consistent hardware and conditions, and avoiding simultaneous Lighthouse runs on the same machine. The agreed three-run median is a project choice, not a promise of identical results. Save every run and explain anomalies rather than selecting only a favorable report. [Lighthouse variability](https://github.com/GoogleChrome/lighthouse/blob/main/docs/variability.md).

CPU slowdown is relative to the host machine. Lighthouse's default simulated throttling models a page load from an observed load and can have edge cases; it is not a physical-device measurement. Record tool/browser versions, host machine, URL, build revision, form factor, viewport, CPU/network settings and storage/cache state so later measurements can be compared. [Lighthouse throttling](https://github.com/GoogleChrome/lighthouse/blob/main/docs/throttling.md).

Navigation mode produces a performance score for a page load. Timespan mode can examine interactions and layout shifts but has no overall performance score. Snapshot mode evaluates the current page state without performance metrics. A snapshot of an already-open staff workspace cannot stand in for the agreed page-load score, and a navigation score cannot alone establish the 100ms pending-feedback condition. [Lighthouse user-flow modes](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md).

The DevTools panel offers a Clear storage option, and the CLI offers `--disable-storage-reset`. Current Lighthouse source is more precise than that broad wording: its default origin-clearing list contains file systems, shader cache, service workers and Cache Storage, and excludes IndexedDB and localStorage. Configurations can change the list. Do not assert that Lighthouse always deletes IndexedDB by default. [DevTools options](https://developer.chrome.com/docs/devtools/lighthouse#advanced-settings), [Lighthouse default settings](https://raw.githubusercontent.com/GoogleChrome/lighthouse/main/core/config/constants.js).

`disableStorageReset: true` skips both configured origin clearing and Lighthouse's disk/memory network-cache clearing. It preserves data from that clearing step, but does not populate a newly opened tab's sessionStorage or make its cache cold. The source clears disk cache with `Network.clearBrowserCache` and evicts memory cache by toggling `Network.setCacheDisabled` true and then false. These commands are distinct from origin-data clearing. [Lighthouse preparation](https://raw.githubusercontent.com/GoogleChrome/lighthouse/main/core/gather/driver/prepare.js), [cache-clearing implementation](https://raw.githubusercontent.com/GoogleChrome/lighthouse/main/core/gather/driver/storage.js).

Puppeteer can create a CDP session attached to the existing page. CDP documents separate network-cache clearing and cache-use control commands; Puppeteer also exposes `page.setCacheEnabled()`. These provide a way to manage HTTP cache separately from the application's persisted data. Check the pinned Lighthouse version's behavior before implementing the measurement script. [Puppeteer CDP session](https://pptr.dev/api/puppeteer.page.createcdpsession), [cache control](https://pptr.dev/api/puppeteer.page.setcacheenabled), [Chrome DevTools Protocol source](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json).

### Proposed measurement protocol

This protocol is an inference from those APIs and the existing tab-session contract. It has not run against an application.

1. Build the locked production revision and serve its actual static output through the Hosting emulator or the agreed hosted destination. Use one fixed target origin per comparison and record its exact URL.
2. For each run, start a fresh Chrome profile, allow normal startup to create the fixed dataset, choose the required language and sign the intended identity in through the demo interface. Disable artificial failures and extra latency. Keep that tab open.
3. Use the same page for the Lighthouse run, through a Puppeteer user flow or the DevTools panel. Explicitly disable Lighthouse storage reset. Assert the intended workspace and identity before beginning. A fresh CLI tab must not assume another tab's sessionStorage.
4. Before measuring the workspace navigation, clear HTTP disk and memory caches separately using the source-described CDP sequence. Preserve IndexedDB and sessionStorage. This measures a navigation with cold HTTP caches and a prepared demo dataset/session; it is not a first-visit seeding measurement.
5. Measure a hard navigation or reload of the exact route in Navigation mode with the recorded mobile Lighthouse configuration. Keep the same browser tab and origin. A scripted navigation callback should perform the hard navigation and await the application's ready/workspace marker before resolving. After collection, assert the exact route, intended identity and rendered workspace marker, and retain the screenshot. Reject a run that measured the chooser, expiry overlay, initialization failure or an unintended shell.
6. Repeat that preparation independently for all three runs, sequentially on the same idle machine. Save HTML/JSON reports and trace artifacts, list each score and CLS, and calculate the agreed median. A measurement failure needs a recorded reason and replacement run, not an invented score.
7. Audit public first-visit startup separately with fresh application storage. Label it separately from the signed-in workspace runs. Browser-local data intentionally retained for a signed-in audit must be documented rather than mistaken for an empty-storage launch.
8. Measure pending feedback separately around deliberately slow actions. Record the trigger and the first painted busy/progress feedback in a browser interaction trace; exclude the intentional operation delay from the feedback interval. Keep language, viewport and action fixed for comparisons.

Lighthouse's documented user-flow API uses an existing Puppeteer page, can perform Navigation-mode loads and can save reports. Its CLI can save HTML, JSON and trace assets. This supports an implementation of the proposed protocol, but the final script must verify retained tab session, intended route rendering, cold HTTP-cache requests and complete workspace capture. Lighthouse does not guarantee that a page's asynchronous application readiness condition has passed. [User-flow API](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md), [CLI report output](https://github.com/GoogleChrome/lighthouse#using-the-node-cli).

## Classic Firebase Hosting checks

Firebase's Hosting configuration uses `hosting.public` to select the deployed directory. Exact static content precedes rewrites, and the first matching rewrite applies. Start's SPA guide still documents a configurable `/_shell.html` default and routing missing paths to that shell while preserving real static assets. Implementation inference: inspect the actual locked build, point Hosting at its static output, and use a catch-all rewrite to its actual shell. Do not assume `/index.html` or a directory name before building. [Hosting configuration](https://firebase.google.com/docs/hosting/full-config), [Start SPA mode](https://tanstack.com/start/latest/docs/framework/react/guide/spa-mode).

The official local workflow uses the Hosting emulator; `firebase serve` is no longer recommended. Firebase documents `--only hosting` to limit emulator startup and `emulators:exec` to run a test script and then shut emulators down. The Hosting default port is 5000. Its CI guide calls out a login prerequisite for Hosting emulator runs, so the eventual runner must verify its authentication arrangement rather than promise that every Hosting test is credential-free. [Local Hosting workflow](https://firebase.google.com/docs/hosting/test-preview-deploy#test-locally), [emulator configuration and execution](https://firebase.google.com/docs/emulator-suite/install_and_configure).

Preview channels publish Hosting content/config at a temporary public URL through `firebase hosting:channel:deploy CHANNEL_ID`. Reusing that channel ID updates the same preview channel. Preview channels normally expire after seven days; a deployment can set expiry up to thirty days. A temporary preview alone therefore does not establish a lasting portfolio delivery URL. The eventual destination and lifetime remain acceptance decisions. [Preview deployment](https://firebase.google.com/docs/hosting/test-preview-deploy#preview-and-share), [channel expiry](https://firebase.google.com/docs/hosting/manage-hosting-resources#set_the_expiration_of_a_preview_channel).

The setup workflow connects local files to a selected Firebase project and creates `firebase.json` and `.firebaserc`. CLI login accesses a Google account, and listing projects checks available access. No chosen project, Hosting site, authenticated deploy identity or preview URL has been established in this repository. These are prerequisites to check when the implementation is ready for publishing. [Hosting setup](https://firebase.google.com/docs/hosting/quickstart), [CLI login and project access](https://firebase.google.com/docs/cli#sign-in-test-cli).

Implementation inference: test direct navigation and refresh for every agreed route on the emulator, including authorized, signed-out, forbidden, final-state and unknown-route entries. Also check real asset URLs, file previews and downloads so a catch-all shell does not conceal missing assets. Rebuild before testing and retain the output path, shell path and Hosting configuration with the result. After an authorized preview/live deployment, repeat those checks on its HTTPS origin with its own seeded browser dataset. Local emulator success cannot prove the hosted configuration or URL works.
