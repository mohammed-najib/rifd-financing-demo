## Startup and recovery

Only an empty state store can receive a seed dataset. A missing dataset beside
other saved records requires recovery, including when the seed transaction
rechecks storage. Unexpected physical stores, unsupported schema/seed/rule
versions, damaged shapes, missing references, mismatched bytes and absent required
canonical/replacement catalog entries refuse readiness without replacing records.
Event sequences cannot exceed metadata's durable sequence. Existing additive
schema-1 support restores absent mutation receipts and catalog product labels.
Invalid raw draft strings and the incomplete Submitted seed remain readable.

Startup probes tab session-storage reads, writes and removal. Storage denial,
failed opening, quota/write refusal, unexpected closure, version changes and
blocked opening have explicit recovery. A refused blocked request aborts if it
later receives an upgrade transaction. Connection loss hides protected content;
retry restores the same dataset and a still-valid tab session. A write abort
retains old saved fields/files and prepared bytes for explicit retry. It never
claims a memory-only save.

Recovery preserves the display language, permits a temporary Arabic/English
switch and keeps public products accessible. Retry reloads saved preferences.
Errors are not marked busy or Ready, and the recovery heading receives focus.
Browser-wide confirmed reset is the next slice's scope; this slice never clears
damaged records to recover.

## Loaded offline use and resources

The stylesheet must be applied, catch-all route preload must return successful
matches, both fonts must be loaded and retained, and required sample bytes must
be durable before readiness. A failed stylesheet can be loaded again on Retry
with a fresh URL. Empty or inaccessible stylesheet rules cannot prove readiness.
The ordinary root stylesheet link permits recovery to render after CSS failure.
Both empty route components disable splitting, so all current route resources
arrive with the entry script. A production test permits only that script and
checks readiness and navigation. Resource errors use the same neutral,
translated recovery screen before protected work is available.

After readiness, both language journeys disconnect the browser, sign in, select
and save a canonical draft sample, preview its saved JPEG, leave and reopen the
draft, inspect products, select and privately save a prepared replacement as
Huda, and open the staff queue and review workspace as Salma. The journeys assert
zero HTTP requests after disconnection. There is no server queue or service
worker. Fresh offline launches remain outside scope. Later routes and assets
must extend this same resource gate.

## Verification

Tests use the accepted public Demo interface with actual IndexedDB and production
screens. Corruption and browser-boundary failure fixtures are isolated in test
files; the product exposes no storage-patching API. Repaired fixtures recover
their original dataset identifiers and permitted records.

The initial red tests reproduced silent seeding of nonempty storage, readiness
with unwritable session storage, missing catalog acceptance and an invalid event
sequence. Screen regressions reproduced lost recovery language and unavailable
session storage at sign-in. Review regressions reproduced readiness after
stylesheet and route-resource failures. Each fix passed its focused checks.

The full pure-domain suite passes all 105 cases. The two packaged-skill tests,
package skill validation/source checks, typecheck, lint and production build pass.
The complete public-interface suite passes all 140 cases. The final focused CSS
failure/retry regression passes. All 402 unique production-screen cases have
passing results, 134 each in Chrome, Firefox and WebKit. All 21 new startup and
offline screen cases pass across those engines.

The six-worker full sweep passed 393 cases in 39 minutes. Nine late WebKit cases
hit their 30-second readiness deadline while still showing neutral loading,
including three existing synchronization cases. All nine passed a one-worker
recheck in 3.9 minutes with unchanged code and timeouts. Resource retry cases
completed in 17 to 20 seconds in that recheck. This supports contention as the
cause of the full-run timeouts. Use fewer workers for subsequent sweeps on this
host. Earlier evidence images regenerated by the suite were restored.

Checked on Omarchy Linux x86_64 with Node 26.7.0, Playwright 1.64.1, installed
Chrome 155.0.8059.39, pinned Playwright Firefox 157.0 and WebKit 27.2. WebKit uses
the compatible launcher documented in [slice 01](01-evidence.md). The production
build retains its existing large-client-chunk warning.

## Standards

The independent review found no documented-standard violations or actionable
baseline smells. It accepted the resource-gate follow-ups too. Domain helpers,
packaged guidance and package intent policy are unchanged.

## Spec

The independent review found two resource gaps. A failed stylesheet could still
allow readiness, and route preloading could swallow lazy-import errors. The
stylesheet gate now requires parsed rules and offers a fresh loading attempt.
The two empty route components load eagerly with the entry script. Regressions
exercise stylesheet failure/retry and allow only the entry JavaScript resource.
The reviewer accepted both fixes and the failed-sheet inspection follow-up.
No other spec gaps or scope creep were found.

Review counts: Standards zero findings; Spec two findings resolved, zero open.
